## Summary

The project is well structured and unusually careful for a course project: the split, the feature pipeline, the label handling and the test-only replay are designed to avoid train/serve skew and direct label leakage, and I found no Critical issue (no label reaches the feature vector, and model selection and threshold tuning do not read the test split). The two most important risks are (1) a poison-pill path in the stream processor, where a single message that passes validation but cannot be scored or inserted (non-UUID `transaction_id`, `Time: Infinity`) fails the micro-batch on every restart, and (2) the AUC-PR used for model selection is computed on the saturated `probability` column, which penalises GBT through tied scores and makes the model comparison partly an artifact. Further Medium risks are near-duplicate rows that may straddle train and test, a retrain path that leaves the producer replaying an outdated test split, selection and threshold tuning on a single 71-fraud validation split, uncalibrated scores presented as probabilities, dashboard threshold state that can diverge from Spark's, and unbounded data growth. Counts: **0 Critical, 2 High, 7 Medium, 5 Low**.

## Details

### R1 · Poison-pill messages crash-loop the stream processor (High)
- **Location:** `src/streaming/transforms.py:42-52` (validation), `src/common/db.py:38-42` (`%s::uuid`), `docker/postgres/init.sql:5` (`transaction_id UUID PRIMARY KEY`), `src/training/features.py:45-47` (`handleInvalid="error"`), `src/streaming/stream_processor.py:171-180`, `docker-compose.yml:186` (`restart: unless-stopped`)
- **Problem:** `is_valid_transaction` checks that required fields are non-null, that inputs are not NaN, that `Amount`/`Time` are `>= 0` and that `source` is known. It does not check that `transaction_id` is a UUID or that the inputs are finite, although its docstring says "finite non-negative inputs". Two inputs therefore pass validation and then fail later in the batch:
  - `"transaction_id": "test-1"` reaches `INSERT ... VALUES (%s::uuid, ...)` and Postgres rejects the cast, which raises inside `foreachPartition`.
  - `"Time": Infinity` (Spark's JSON reader accepts non-numeric numbers; the existing test at `tests/unit/test_streaming.py:90` relies on this for `NaN`) is not NaN and is `>= 0`, so it passes. `PMOD(Time / 3600, 24)` then yields NaN, `hour_sin`/`hour_cos` become NaN, and `VectorAssembler(handleInvalid="error")` throws.
  
  In both cases the exception fails the micro-batch, the query terminates, `main()` returns 1 and Docker restarts the container. The checkpoint replays the same offsets, so the failure repeats. This was derived from the code, not run.
- **Impact:** One hand-written message on `transactions` (the topic is reachable from the host on `localhost:9094`, which exists for host tools) stops all scoring until the message ages out after 24 h or the volumes are reset. In the UUID case the Kafka writes happen before the Postgres write (`src/streaming/batch.py:76-80`), so each restart also re-publishes the batch (up to `maxOffsetsPerTrigger` rows) to `predictions` and `fraud-alerts`. The producer and the dashboard build messages through pydantic, so they cannot send such a message; the exposure is manual or third-party producers.
- **Suggested fix:** In `is_valid_transaction`, add `F.col("transaction_id").rlike("^[0-9a-fA-F]{8}-([0-9a-fA-F]{4}-){3}[0-9a-fA-F]{12}$")`, reject infinities for every column in `RAW_INPUT_COLUMNS` (for example `F.abs(F.col(name)) < F.lit(float("inf"))` alongside the NaN check) and require `replay_pass >= 0`. As a second line of defence, catch `psycopg.errors.DataError` / `IntegrityError` in `write_partition_to_postgres`, retry the buffer row by row and log the rejected rows (or publish them to a dead-letter topic) so that data errors never fail the batch. Add both payloads to `test_invalid_messages_are_filtered`.

### R2 · Selection metric computed on saturated probabilities (High)
- **Location:** `src/training/evaluate.py:50-52`, `src/training/train_model.py:162` and `:175-179` (selection per combination), `:315` (final selection), `docs/RESULTS.md:25-26`, `PROGRESS.md:79`
- **Problem:** `spark_auc_metrics` builds the evaluator with `rawPredictionCol=PROBABILITY_COL`, so AUC-PR and ROC-AUC rank rows by `probability[1]`. For GBT that value is a logistic transform of the boosted margin, and it saturates: PROGRESS.md states "Its probabilities saturate near 1, which creates many tied scores". Tied scores at the top of the ranking collapse the high-precision part of the PR curve into one point, so the metric measures floating-point saturation as well as ranking quality. The results show the effect: GBT with class weights has validation AUC-PR 0.4776 and test AUC-PR 0.7679, and GBT with undersampling 0.3553 and 0.4210, while every other family moves by at most about 0.09 between the two splits. I could not measure the number of ties (the data and model are out of scope), so the size of the deflation is unknown; the mechanism is confirmed by the code and by the author's own note.
- **Impact:** Model selection uses this metric, so GBT is compared on a different footing from the other three families and may have been excluded for a numeric reason. The comparison table and the observation in `PROGRESS.md:77` ("AUC-PR ranges from 0.42 to 0.84") are partly an artifact, which matters because the four-model comparison is a headline deliverable.
- **Suggested fix:** Compute the ranking metrics on the unsaturated score: `rawPrediction` for LR, RF and GBT, and `svm_raw` for the SVM (pass the column name per `ModelSpec`). Keep `probability` only for the threshold-dependent metrics. Re-run training and regenerate `RESULTS.md`. If GBT is then selected, note that its alert threshold has limited resolution near 1.0, or threshold on the margin. Add a unit test with scores that tie in `probability` but not in `rawPrediction`.

### R3 · Near-duplicate rows can straddle train and test (Medium)
- **Location:** `src/training/data_prep.py:128-137` (`dropDuplicates()` on all columns), `src/training/data_prep.py:163` (split key hashes all columns), `src/training/features.py:27-37` (raw `Time` is replaced by hour-of-day)
- **Problem:** Duplicates are removed only when the entire row matches, including `Time` and `Class`. The model never sees raw `Time`; it sees `V1..V28`, `log1p(Amount)` and the hour of day. Two rows with identical `V1..V28` and `Amount` but different `Time` are therefore kept, hashed to different split keys and can be assigned to train and test respectively. If they fall in the same hour they are identical in feature space. The split is also random rather than temporal, so bursts of similar fraudulent transactions are spread across all three splits. I did not measure how many such rows exist, because `data/` is out of scope for this review; treat this as a leakage risk to quantify, not a confirmed inflation.
- **Impact:** If the count is material, test AUC-PR, precision and recall in `docs/RESULTS.md` are optimistic, and the live quality panel is too, since the producer replays that same test split. The statement in `docs/RESULTS.md:65` ("no identical transaction appears in both training and test data") holds only for full-row duplicates.
- **Suggested fix:** First measure: count rows that are duplicated on `V1..V28 + Amount` (and on those plus `Class`) and how many of those groups span more than one split. If non-trivial, either de-duplicate on the model's input columns, or assign whole duplicate groups to one split (hash only `V1..V28, Amount` for the split key). Report the count in `RESULTS.md`. Consider adding a time-ordered split as a robustness check, and state in the report that the split is random.

### R4 · Retraining leaves the producer on an outdated test split (Medium)
- **Location:** `run.ps1:236-242`, `src/producer/producer.py:130`, `src/producer/replay.py:53-61`, `src/training/train_model.py:293-294`
- **Problem:** `Invoke-Train` runs the trainer with `--force` and then restarts only `stream-processor`. The producer loads `test.parquet` once at startup (`load_replay_dataset`) and keeps it in memory. The trainer rewrites `data/processed/{train,val,test}.parquet` on every run. With the same seed and dataset the split is identical, so nothing changes. If `RANDOM_SEED` or the CSV changed, the new model is trained on a different 70 %, and the running producer keeps streaming the old test rows, most of which are now training rows. `docker compose restart` also does not re-read `.env`, so the restarted stream processor keeps its old environment.
- **Impact:** After such a retrain the Live Monitor's precision, recall and confusion matrix are computed on data the deployed model was trained on, with no visible sign. Separately, running the 3 GB trainer next to the live stack exceeds the roughly 6 GB budget in `PLAN.md:340`, which assumes streaming waits for training.
- **Suggested fix:** After a successful retrain, recreate both services (`docker compose up -d --force-recreate producer stream-processor`). Make the mismatch detectable: write the `run_id` next to the splits (for example `data/processed/split_meta.json`), have the producer compare it with `metrics.json` at startup and refuse to start on a mismatch, and carry `run_id` in the prediction rows. Consider stopping `producer` and `stream-processor` before the trainer starts.

### R5 · Selection and threshold tuning on a single 71-fraud validation split (Medium)
- **Location:** `src/training/train_model.py:175-179` and `:315` (selection by validation AUC-PR), `src/training/train_model.py:195-196` and `src/training/evaluate.py:97-108` (max-F1 threshold on the same split), `docs/RESULTS.md:21-28`
- **Problem:** Sixteen candidates are ranked on one validation split that contains 71 frauds, and the alert threshold is then tuned on the same 71. The best three validation scores are 0.7985, 0.7869 and 0.7804, while the same models move by 0.04 to 0.09 between validation and test (0.7985 to 0.8408, 0.7869 to 0.7295, 0.7804 to 0.6985). The ranking is therefore within sampling noise. No confidence intervals are reported.
- **Impact:** The test numbers remain an honest estimate for the chosen model, because test is not used for selection. What is not supported is the conclusion that Random Forest with class weights is the best of the eight combinations, or that a threshold of 0.3863 is near-optimal; a different seed could plausibly select a different model.
- **Suggested fix:** Select with stratified k-fold cross-validation over train+val (5 folds gives about 400 frauds of evaluation in total), or repeat the split over several seeds and average. Report bootstrap confidence intervals for test AUC-PR, precision and recall. State the limitation in `RESULTS.md`.

### R6 · Uncalibrated scores presented as fraud probabilities (Medium)
- **Location:** `src/training/train_model.py:158-161` and `src/training/models.py:129-140` (calibration only when `needs_calibration`), `src/streaming/transforms.py:57-59` (`fraud_probability`), `src/training/report.py:305-317` (methodology notes), `PLAN.md:452`
- **Problem:** Platt scaling is applied only to the SVM. The other models are trained with balanced class weights (fraud weight about 300) or 1:10 undersampling, both of which shift the predicted probabilities upward relative to the true 0.17 % prevalence. The deployed model is the class-weighted Random Forest. Its output is published as `fraud_probability`, shown on a probability gauge and described as "fraud probability" throughout. `PLAN.md:452` lists this as a risk that is "Documented as a limitation", but the methodology notes generated into `RESULTS.md` do not mention it.
- **Impact:** Ranking and thresholding are unaffected, so alerts are correct. The number shown to users is not a probability: a value of 0.39 does not mean a 39 % chance of fraud, and thresholds are not comparable across models (0.386 for RF, 0.945 for LR in the same table).
- **Suggested fix:** Either calibrate the selected model (Platt or isotonic regression on a calibration split that is not the one used for threshold tuning; with R5's cross-validation, use out-of-fold scores), or keep the current behaviour and add the limitation to the methodology notes in `report.py` and label the UI value "fraud score".

### R7 · Dashboard threshold state can diverge from Spark's (Medium)
- **Location:** `src/dashboard/sidebar.py:34-39` (`_init_threshold`), `:48-52` (`_reset_threshold`), `:59-63` (slider range), `src/dashboard/views/live_monitor.py:28-29`, `src/dashboard/helpers/queries.py:18` and `:34-37`, `src/common/config.py:154`, `src/common/db.py:97-102`
- **Problem:** Three separate issues share one cause, namely that the dashboard keeps its own copy of the threshold in session state:
  - `_init_threshold` returns early once the key exists, so a session never re-reads Postgres. A change made in another browser session, by `ALERT_THRESHOLD_OVERRIDE`, or by the reset in `sync_threshold_with_model` after a retrain is not picked up. The Live Monitor queries count `fraud_probability >= %(threshold)s` with the session value, so its flagged count, fraud rate and quality panel describe a threshold Spark is not using.
  - The value is rounded to 3 decimals on init and on "reset to model default", so the reset stores 0.386 while the tuned threshold is 0.3863. Rows scoring between the two are flagged by the dashboard's reset value but were not flagged in the reported test metrics.
  - The slider accepts 0.01 to 0.99, while the config and `validate_threshold` accept any value in (0, 1), and a max-F1 threshold can exceed 0.99 (GBT with undersampling tuned to 0.988 in this run). I did not verify how Streamlit 1.66 handles a session value outside a slider's range; it either raises or shows a clamped value while Spark keeps the real one.
- **Impact:** The headline KPIs can disagree with the `fraud-alerts` topic and with the `prediction` column, and two users see different numbers. The out-of-range case would affect every page, because the sidebar renders on all of them.
- **Suggested fix:** Read the threshold from Postgres at the start of each fragment refresh and use that value in the queries; update the slider's session value when the database value changes. Store and display the unrounded threshold (use `step=0.0001` or a number input). Widen the slider to 0.001 to 0.999 or clamp on init, and constrain `alert_threshold_override` to the same range.

### R8 · Unbounded growth and full-table KPI scans (Medium)
- **Location:** `src/dashboard/helpers/queries.py:15-40` (`KPI_SUMMARY_SQL`, `QUALITY_SQL`), `:54-60` (`RECENT_ALERTS_SQL`), `docker/postgres/init.sql:21-26`, `src/common/db.py:185-187` (only `stream_progress` is pruned), `docker/kafka/create-topics.sh:33-34`, `src/common/kafka_utils.py:15-22`
- **Problem:** The producer loops forever at 50 tx/s and the long-running services use `restart: unless-stopped`. Nothing prunes `predictions`: at the default rate that is about 4.3 million rows per day. `KPI_SUMMARY_SQL` and `QUALITY_SQL` aggregate over every `source = 'replay'` row with a filter on `fraud_probability`, which no index covers, and they run every 2 s for each open browser session against a Postgres limited to 256 MB with 64 MB of shared buffers. `RECENT_ALERTS_SQL` filters on `fraud_probability >= threshold`, which cannot use the partial index on `prediction = 1`. On the Kafka side, `transactions` and `predictions` have a 24 h time retention but no `retention.bytes`, and the producer sends uncompressed JSON. `PLAN.md:456` acknowledges the row growth and describes the queries as "indexed time-window queries", which is true only for the 60 s window columns.
- **Impact:** After a few hours the Live Monitor refresh becomes slow and Postgres CPU-bound; left running for days, the Postgres and Kafka volumes grow by gigabytes per day inside the Docker Desktop disk image. For a short demo this does not matter.
- **Suggested fix:** Prune `predictions` to a retention window (for example delete rows older than a few hours from the progress listener, as already done for `stream_progress`), or keep running totals in a small counters table updated per batch. Limit the quality and KPI queries to a time window that uses `idx_predictions_source_processed_at`. Add `retention.bytes` to the two large topics and `compression.type=lz4` to `producer_config`.

### R9 · Test gaps around the riskiest paths (Medium)
- **Location:** `tests/unit/test_streaming.py:81-94`, `tests/unit/test_common.py:123-125`, `pyproject.toml:27-32`, `docker-compose.yml:238`, `run.ps1:282`
- **Problem:**
  - `test_invalid_messages_are_filtered` covers eight malformed inputs but not a non-UUID `transaction_id` or an infinite value, which are the two inputs that break the batch (R1).
  - The insert statement is checked only as a string (`"%s::uuid" in ...`) and against fakes. Nothing checks `PREDICTION_DB_COLUMNS` against the columns and constraints in `docker/postgres/init.sql`, so drift between the two would pass every unit test.
  - `src/dashboard/sidebar.py` is excluded from coverage, and it contains real logic (threshold init, rounding, reset, control-state derivation) behind R7 and R11.
  - There is no test that scoring ignores `actual_class` (for example, identical probabilities when the label is flipped), which would be a cheap guard against a future leakage regression.
  - `tests/e2e` does not exist, while the `e2e` service runs `pytest tests/e2e` and `run.ps1 e2e` invokes it. PROGRESS.md schedules this for Phase 6, so this is expected at this stage; until then the Kafka source, the sinks and `main()` of the stream processor have never been exercised together.
- **Impact:** The 95.9 % coverage figure overstates the protection on the streaming failure paths and the database contract.
- **Suggested fix:** Add the two payloads to the malformed-input test; parse `init.sql` in a test and compare its column names with `PREDICTION_DB_COLUMNS` (or run the insert against a real Postgres in the e2e suite); move the sidebar's pure logic into `helpers/` and test it; add the label-flip test; write the e2e suite in Phase 6.

### R10 · `latency_ms` excludes inference and sink time (Low)
- **Location:** `src/streaming/transforms.py:65-70`, `PLAN.md:280`
- **Problem:** `processed_at = F.current_timestamp()` is fixed when the batch's query execution starts, as the docstring itself notes ("fixed once per query execution"). That moment is before the model runs and before any sink write. The same docstring and `PLAN.md:280` nevertheless define the latency as covering "model inference" / "model scoring".
- **Impact:** The reported processing latency is lower than the real time to a scored result by roughly the batch's scoring time. The end-to-end figure based on `stored_at` is unaffected.
- **Suggested fix:** Reword both definitions to "Kafka queueing plus trigger wait, up to the start of scoring", or compute the latency from a timestamp taken after scoring.

### R11 · Producer-control edge cases (Low)
- **Location:** `src/dashboard/resources.py:91-94`, `src/dashboard/helpers/kafka_io.py:80`, `src/dashboard/sidebar.py:85-94`, `src/producer/producer.py:148-156` and `:184`, `src/producer/control.py:100-101`
- **Problem:**
  - `last_control_command` returns `None` both when no command was ever sent and when the read failed or timed out. `_send_control` then derives the "current" state from the defaults (`paused=False`), so applying a rate while the producer is paused and Kafka is briefly slow publishes a full-state command with `paused=false`.
  - The producer starts the control listener and begins replaying immediately, so after a restart it sends at the default rate until the listener has read the retained command. PLAN.md says the last command "survives restarts"; it does, after a short burst.
  - If the listener thread hits an unexpected exception it logs `control.listener_crashed` and exits; the producer keeps running and ignores all later commands, with no health signal.
- **Impact:** Unintended resume in a narrow window; a short burst after restart while paused; silent loss of control after a listener crash.
- **Suggested fix:** Return a distinct "unknown" state from the read and disable the control buttons while it is unknown. In the producer, wait until the listener has reached the control topic's end offset (bounded by a timeout) before starting the replay. Restart the listener loop on error, or stop the heartbeat so the container turns unhealthy.

### R12 · Secrets wider than needed (Low)
- **Location:** `docker-compose.yml:63`, `:124`, `:139`, `:223`, `:239` (`env_file: .env`), `docker-compose.yml:290`, `.gitignore:9-10`, `.dockerignore:6`
- **Problem:** `env_file: .env` injects every variable, including `POSTGRES_PASSWORD`, into `kafka-init`, `trainer`, `producer`, `tests` and `e2e`, none of which connect to Postgres (the e2e service will, once it exists). Separately, the downloader mounts `${KAGGLE_CONFIG_HOST_DIR:-./.kaggle}`; that default directory inside the repository is not listed in `.gitignore` or `.dockerignore`, so a Kaggle token placed there could be committed or sent in the build context.
- **Impact:** Low for a localhost-only course project (all ports are bound to 127.0.0.1); it is a least-privilege gap and a small risk of committing a credential.
- **Suggested fix:** Give each service an explicit `environment:` list (or split the file into `.env` for Compose and per-service env files), and add `.kaggle/` to both ignore files.

## What looks good

- No direct label leakage: `Class` and `actual_class` are not in `FEATURE_COLUMNS`, the feature list is a single constant, and the producer, the Test page and the demo samples all draw from the test split only.
- The feature pipeline is fitted on the training frame and saved inside the `PipelineModel`, so streaming applies the same transforms as training.
- Validation and test keep the real class balance; undersampling and class weights touch the training frame only; selection and threshold tuning read validation, never test.
- The exact, content-hashed stratified split is reproducible and independent of row order, and is tested for disjointness and completeness.
- AUC-PR is computed without MLlib's default binning (`numBins=0`), with scikit-learn's average precision reported as a cross-check and a regression test for it.
- Streaming design: one query with `foreachBatch`, scored result cached once for three sinks, idempotent `ON CONFLICT DO NOTHING` insert, checkpoint on a named volume, threshold read per batch with a last-good fallback, monitoring that cannot fail the query.
- Kafka setup: separate internal and external listeners, auto-create disabled, idempotent producer with `acks=all`, full-state control messages on a compacted topic read from the beginning.
- Malformed JSON, missing fields, bad timestamps, unknown sources and NaN inputs are filtered rather than failing the batch.
- Docker and Windows: pinned images and dependencies, connector jars fetched and checksummed at build time, non-root users, every host port bound to 127.0.0.1, read-only Kafka UI, LF normalisation plus CR stripping, memory limits per service, atomic artifact writes that avoid Hadoop renames on bind mounts.
- `run.ps1` avoids PowerShell 7-only syntax, checks native exit codes, writes `.env` without a BOM and generates a random database password.
- SQL is parameterised throughout; settings are typed and fail fast on missing endpoints; logging is structured JSON.
- Pure logic is separated from Streamlit and Spark glue, which makes most of it unit-testable, and the unit suite is broad.
